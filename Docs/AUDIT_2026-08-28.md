# Full project audit — 2026-08-28

Static audit scope: all 94 C# scripts in `Assets/CatsAndKills/Scripts`, plus package/build settings and current scene-builder pipeline.

## Critical issues fixed on this branch

- Depth sorting was non-idempotent: renderers reused already-absolute `sortingOrder` values as local offsets every frame.
- Concept polish disabled collider-backed wall faces even when replacement art was missing or failed to render.
- Two competing character render pipelines were installed into the same generated scene and one replaced the other on the first Play frame.
- Hold/Suppress enemies cancelled their own path to cover on the next decision tick.
- Navigation failure was indistinguishable from actually reaching a destination.
- Flank destinations could fail and still be treated as completed.
- Enemy facing rotated a dynamic Rigidbody2D root directly; perception now owns facing independently.
- Enemy LOS used root/feet positions instead of combat-height points.
- Character presentation used unscaled time while gameplay physics used scaled time.
- Hitscan/muzzle FX used a hard-coded root offset instead of the visible weapon position.
- Enemy separation allocated a new collider array every FixedUpdate.

## Architecture findings still requiring follow-up

### Animation
The current production character art contains only two movement frames per direction and the runtime animation is code-driven, not Animator-driven. No amount of timing tuning can make two poses look like a genuinely fluid walk/run. The correct next step is either:
1. author/generate 6–8+ locomotion frames per direction and drive them with AnimationClips/Animator, or
2. split characters into riggable parts and use Unity 2D Animation/Sprite Skin.

### Scene source of truth
The tracked Build Settings referenced `Assets/Sandbox.unity`, while the actual builder generates `Assets/CatsAndKills/Scenes/PlayableCombatSandbox.unity`. The generated scene is not committed, so after a clean checkout the builder must be run before the scene can be treated as valid.

Long-term, runtime/editor builders should stop being the primary authoring format for the entire level. Stable gameplay prefabs and committed scene assets should become the source of truth; editor builders can remain import/conversion tools.

### Rendering
The project still relies heavily on custom numeric sorting orders. Prefer explicit Sorting Layers / Pivot sort points / SortingGroup where appropriate, and keep custom Y-ordering narrow and deterministic.

### AI/navigation
The navigation grid is static after Build/Configure. Door/destructible state changes can make its walkability stale.
Pathfinding uses a linear List open-set and resets every grid node per query. This is fine for a tiny prototype but will spike as enemy count/map size grows.
Cover points are authored separately from navigation validity; unreachable candidates are now rejected by the brain, but candidate scoring should eventually include path cost and exposure.

### Runtime allocations/performance
Remaining hot paths include:
- grenade scans via `FindObjectsByType`
- several `OverlapCircleAll` / `RaycastAll` queries
- combat FX created/destroyed as new GameObjects
- repeated runtime character verification scans
- A* allocating a new path/open collections per request

Before scaling encounters, move transient FX to `UnityEngine.Pool.ObjectPool<T>`, use reusable physics-query buffers/ContactFilter2D, and profile with GC.Alloc visible.

## Required editor validation after checkout

1. Open with Unity `6000.5.10f1`.
2. Run `Tools > Cats and Kills > Build Playable Concept-Art Version`.
3. Confirm the generated scene path is `Assets/CatsAndKills/Scenes/PlayableCombatSandbox.unity`.
4. Enter Play Mode and verify:
   - walls remain visible;
   - exactly one character visual exists per combatant;
   - muzzle flash originates at the weapon;
   - Hold/Suppress enemies complete their movement to cover;
   - failed flank paths do not instantly complete;
   - pause/slow motion affects character presentation.
5. Use Window > Analysis > Profiler and inspect CPU Usage + GC.Alloc during a firefight.
